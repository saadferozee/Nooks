2.4 Move delivery logic into the database (HIGH PRIORITY)
----------------------------------------------------------------
This is the single highest-leverage change - it removes the
INSERT/UPSERT race condition at the source instead of patching it
client-side.

create or replace function public.handle_new_message()
returns trigger
language plpgsql
security definer
as $$
begin
  insert into message_status (message_id, user_id, status)
  select new.id, cp.user_id, 'delivered'
  from conversation_participants cp
  where cp.conversation_id = new.conversation_id
  and cp.user_id != new.sender_id
  on conflict (message_id, user_id) do nothing;

  return new;
end;
$$;

create trigger on_message_inserted
  after insert on messages
  for each row execute procedure public.handle_new_message();

3.2 Batch status updates
-----------------------------
[ ] Collect all currently-unread message IDs for the open
    conversation into an array
[ ] Send ONE upsert call with the full array of rows
[ ] Remove the forEach loop from Phase 4 step 7 that calls upsert
    per message - replace with a single batched call:

const unreadIds = messages
  .filter((m) => m.sender_id !== user.id)
  .map((m) => m.id);

if (unreadIds.length > 0) {
  await supabase.from("message_status").upsert(
    unreadIds.map((id) => ({ message_id: id, user_id: user.id, status: "read" })),
    { onConflict: "message_id,user_id" }
  );
}

3.3 Prevent continuous read-update loop
--------------------------------------------
[ ] Read-status update should fire ONLY when the chat is first
    opened, or a new unread message arrives while already open
[ ] Must NOT fire on every re-render
[ ] Use a ref tracking "already marked read up to message X" to
    guard this (see 3.7)

3.4 Prevent duplicate messages (fetch + realtime overlap)
